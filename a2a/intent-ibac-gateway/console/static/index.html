the preview takes in

  • the intent - the Intent Agent's artifact, {prompt, evaluations[]}. Of each evaluation it compares the subject type, the action name and the resource type; ids are read only at usage, the prompt text never.
  • a capability - an agent card reduced to its name and its skills: id, name and the skill's x-coaz-mappings. One per agent; the console gives it every card of the fleet in turn.
  • params - what $references in the mappings resolve from, two keys and nothing from the intent: token, the delegated token's claims ($token.sub is the caller), and request, the parameters of the call ($request.arguments.tier). A message carries no arguments, so the preview stands them in with the context.parameters of the intent.

the preview gives back

  • a decision - true or false, with a reason code and, when negative, a reason in words.
  • discovery - for every evaluation, the ids of the skills that matched it; the card is AUTHORIZED when any evaluation matched any skill.
  • usage - for the one skill it was given, the step of a tool call (an A2A message has none): either the generated AuthZEN requests ({subject, action, resource, context.input_params}, ids resolved from the call's arguments and the token) or nothing when the match is a search.
  • one audit record per call - IBAC_DISCOVERY with the skills matched per evaluation, IBAC_USAGE with the skill id and the reason code.

the preview never

  • an ALLOW or DENY: that is the platform's answer to the generated requests
  • a change to the intent or to the message
  • a look at the prompt text, the token signature or the graph

Intent-Based Access Control, in five steps.

        
An agent says what it can do. A prompt says what someone wants. IBAC checks that the two agree before a message is forwarded to an agent, and names the exact permission to verify. Every example below uses the real cards and policies of this demo.

      


      

        

          
1

          

            
Two sides of one question

            
On one side, the Intent Agent has turned the prompt into an intent: one or more evaluations of the form subject → action → resource, in the vocabulary of the graph's policies. On the other side, every agent publishes an agent card that lists its skills. IBAC adds one thing to each skill: a declaration of which subjects may do which actions on which resources through it. The engine never reads the prompt. It reads the intent and the declarations.

2

          

            
A mapping, field by field

            
The declaration lives on the skill under the key x-coaz-mappings (coarse authorization mappings). A skill can carry several; each one is a small table with three columns and one optional context.

            


{
  "id": "quote-lookup",
  "name": "Quote lookup",
  "x-coaz-mappings": [
    {
      "subject":  [{"type": "Person", "id": "$token.sub"}],
      "resource": [{"type": "Quote", "id": "stock_quote"}],
      "action":   [{"name": "CAN_RETRIEVE"}, {"name": "GET_PRICE"}]
    }
  ]
}

              

                
subjectOne or more types of caller the skill serves (here always Person: every login is one). The id is almost always $token.sub: whoever is in the token.

                
resourceOne or more types of thing the skill touches. The id is a literal when the skill is bound to one resource, a $reference when the prompt names it, or empty when the skill works on "whichever ones you may".

                
actionThe actions, named exactly as the graph's policies name them. No action listed means any action.

                
contextFree-form notes for the operator; the engine does not read it.

              

            

          

        


        

          
3

          

            
Discovery: who could serve this?

            
The engine takes each evaluation of the intent and asks every skill of every card the same three yes/no questions. Three yes on one mapping and the skill is a match. Ids are deliberately ignored at this stage: discovery runs before anyone has resolved who exactly is asking about what. One matching skill anywhere makes the card AUTHORIZED; none makes it NOT_AUTHORIZED with the reason intent_mismatch. A card with no mappings at all is settled by the gateway's setting before the engine is asked: allow, the default, skips the mapping check for it and KBAC alone decides; deny hands it to the engine, which answers missing_coaz_mapping. The switch next to the composer sets it for the preview.

4

          

            
Usage: what exactly must be checked?

            
Usage is the step of a call that names a capability: an MCP tools/call, resources/read or prompts/get. It confirms the current intent against that one capability and turns the mapping into concrete AuthZEN requests. Now the ids matter. A literal stays as it is. A $reference is looked up in what the call carried, never in the intent: $token.sub in the delegated token's claims, $request.arguments.tier in the arguments of the call. One request is built per resolved (subject, resource) pair, with the evaluation's action. An A2A message names no capability and carries no arguments, so it has no usage step; the preview below runs it anyway, as what a tool call on the matched skill would be checked against, with the arguments stood in by the parameters the Intent Agent extracted.

A reference that cannot be resolved drops that entity, and the mapping does not match: a skill bound to $request.arguments.tier is not a match for a call that carries no tier (in the preview, a prompt that named none). 5

          

            
Where the engine stops

            
The engine answers one question: does this agent declare the skill this intent needs, and which permission does that come down to? It makes no authorization decision. The generated requests go to the platform's AuthZEN API, which evaluates the graph policies and answers ALLOW or DENY; a search match is decided from the intent's own evaluation. Every engine call is audited: one IBAC_DISCOVERY record per card, with the skills matched per evaluation, and one IBAC_USAGE record per confirmed skill, with its reason code.

What each agent declares it can do.

        
Six agent cards. Every skill carries x-coaz-mappings: the subject types, resource types and actions it serves, in the vocabulary of the project's policies. The mapping check never reads a prompt - it reads these. And each gateway shows a person only the skills they may use: the authenticated card is filtered to the CAN_USE Skill set the platform answers for them, which the marks below come from.

      

      

      

        

          1
          
Discovery

          
The intent against every skill of a card. A skill matches an evaluation when one of its mappings agrees on the subject type, the resource type and the action. Ids are not compared yet. One match anywhere is a positive decision. A card without mappings is settled by the gateway's setting first: allow (default) skips the check and KBAC alone decides, deny refuses it (missing_coaz_mapping).

        

        

          2
          
Usage

          
The step of a tool call (an A2A message has none): the current intent against the one capability the call names. The matching mapping's ids are resolved from the call and one AuthZEN request is built per (subject, resource) pair: intent_match_authzen_required. Ids left empty mean a search match, intent_match_search: nothing is generated, the intent's own evaluation decides.

        

        

          $
          
References

          
An id starting with $ is looked up in what the call carried, under two keys: $token.sub is the caller from the delegated token, $request.arguments.tier an argument of the call. Nothing comes from the intent. A reference that does not resolve drops the entity, and the mapping does not match.

        

      

      

        

          
What a coaz mapping is

          
coaz is short for coarse authorization: a statement on a skill of what it is for, coarse because it names types, not instances. A skill carries them as a list under the key x-coaz-mappings, next to its id, name and description on the A2A agent card. An MCP tool, resource or prompt carries the same list in its _meta. The key starts with x- because it is an extension the card format does not know; a client that does not understand it ignores it, a gateway that does reads it before forwarding anything.

          
One mapping says: callers of these subject types may perform these actions on resources of these resource types through this skill. Several entities in one list are a cross product (two subject types and two resource types make four combinations). Several mappings on one skill are alternatives: the skill matches when any one of them does.

          

            
subjectat least one entity; type is a node type of the graph (a letter or underscore then word characters, 2 to 64), id optional

            
resourcesame rules as subject

            
actionzero or more names, exactly as the policies spell them; none means any action

            
contextan optional map for operators; the engine does not read it

            
idsliteral bound to one instance · $reference resolved at usage from the call's arguments or the token ·empty any instance, a search

            
limits64 mappings per skill, 64 entities per list, 64 actions; an invalid mapping makes the gateway refuse the whole card. An intent carries at most 10 evaluations: a larger one is refused before the exchange and the caller is asked to split the prompt

          

        

        

          
How to write one

          
Start from the policies, not from the prompt: every (subject type, action, resource type) in a mapping must exist as a policy, or the Intent Agent will never emit it and the mapping is dead weight. Bind the subject to $token.sub: the caller is whoever the delegation token says, never a value from the prompt. Pin the resource id only when the skill really serves one instance (stock_quote, cs_policy); use a $request.arguments.<name> reference when the call carries that argument and the policy declares the parameter; leave it empty when the skill answers "which ones may I".

          
Keep a skill's mappings narrow. A mapping with no actions matches every action on those types, which is rarely what a skill means. Group by what the skill does, not by what the agent could do: discovery routes to skills, and a card whose one skill maps everything tells the engine nothing.


"skills": [{
  "id": "my-accounts",
  "name": "My accounts",
  "x-coaz-mappings": [
    { "subject":  [{"type": "Person", "id": "$token.sub"}],
      "resource": [{"type": "AccountTier", "id": "$request.arguments.tier"}],
      "action":   [{"name": "HAS"}] },
    { "subject":  [{"type": "Person", "id": "$token.sub"}],
      "resource": [{"type": "AccountTier"}],
      "action":   [{"name": "HAS_TIER"}] }
  ]
}]
