One prompt, end to end

  1. Login. The person logs in at Auth0 (authorization code with PKCE, the tenant's "Console" application); the console keeps the access token issued for the people's API, aud ibac-people, in a server-side session. Every login is a Person of the graph.
  2. SendMessage. A2A JSON-RPC to the gateway of the chosen agent with Authorization: Bearer <the person's Auth0 token>, A2A-Version: 1.0 and X-Request-ID. From here on the gateway drives.
  3. Introspect. The gateway validates the Bearer at the auth0-bridge (RFC 7662; the bridge verifies the JWT against the tenant's JWKS) and accepts only a token issued for ibac-people; it also fetches its own client-credentials token through the bridge, with its Machine-to-Machine application. Tampered, wrong-audience or missing tokens are 401 before anything else happens.
  4. Exchange. RFC 8693 at the Token Service: the person's Auth0 token as subject, the gateway's as actor, both verified against the tenant JWKS; a delegated token out with aud intent-ibac-agents, sub = the person, act.sub = the gateway's client subject. One more hop per gateway.
  5. whoami. The platform resolves the person's token to its Person node through the dataset's auth0-people token introspect (the tenant's issuer and keys). Whether that person is staff or a customer is found on the graph (WORKS_IN, IS_CUSTOMER), never in the token.
  6. Admission. One AuthZEN evaluation: subject = the whoami result, action CAN_TRIGGER, resource = the gateway's own Agent node, the chain in $ik_token.act_chain. The policy person-can-reach-agent compares it with the Workflow → INVOKES → Agent path. false is a 403, before the prompt is read.
  7. Intent. With ibac.enabled the gateway sends the prompt to the Intent Agent, the whoami subject in message.metadata, its own token as Bearer. The agent introspects that token at the bridge with its own M2M client, reads the data schema and the subject type's ACTIVE policies (cached in Redis), extracts with Gemini, validates, audits. No intent, and the gateway answers the caller itself with the agent's reason; the agent behind it is never called. With an intent, a gateway that passes it on exchanges once more, same subject and actor plus the evaluations, and the Token Service writes them into act.intent; more evaluations than it takes (10), and the gateway asks the caller to split the request instead.
  8. Forward. The message reaches the agent with the delegated token in X-IK-Token (the one of the second exchange, with the intent, when there was one) and the delegated token extension named in A2A-Extensions; Authorization is left empty (authorization_header.forward: none), so the agent never holds the person's token and cannot start a new workflow as them. The stand-in agent echoes what it received, so the trace shows the chain arriving.
  9. Decide the intent. The console maps each evaluation to the AuthZEN endpoint the platform has today and shows the live decision or search results. filters and qualifiers are shown as carried: the AuthZEN API reads input_params only.
  10. Discover. The mapping preview matches the intent against every card of the fleet: a skill matches an evaluation when one of its x-coaz-mappings agrees on subject type, resource type and action.
  11. Confirm. For every matched skill the preview runs usage as a tool call would see it (an A2A message has no usage step): it resolves the mapping's ids ($token.sub from the delegated token, $request.arguments.<name> from the call's arguments, stood in by the intent's parameters) and builds one AuthZEN request per (subject, resource) pair, or declares a search match when an id stays empty.
  12. Decide the generated requests. The requests the preview built go to the platform through the same mapper as the intent's own evaluations, so the board shows ALLOW or DENY next to each.

Boundaries

Three things leave the machine: the login and the bridge's calls to the Auth0 tenant, the platform calls (whoami, admission, schema, policies, decisions) and the Gemini call made by the Intent Agent. Secrets live in .env (the tenant's client secrets among them) and in two generated files that git ignores: the Token Service config and the gateways' audit config.

The Intent Agent makes no authorization decision. It produces the question, in the AuthZEN shape, from the only vocabulary a policy engine will accept.
The gateway makes one decision, admission: may this caller reach this agent through this delegation chain. The mapping preview makes none. It answers a narrower question, in the console: does this card declare a skill for this intent, and which permission does that come down to? A gateway that reads the mappings filters its authenticated card to the skills that fit the intent in the delegated token; the console asks for the cards with the person's token, which carries no intent, and a message is forwarded on admission and intent alone, which is why that part stays a preview here. There is no central engine and nothing routes: each gateway checks its own card, so the fleet is compared by sending the same prompt through each gateway.

What the fleet is

Six A2A agent cards in console/data/fleet.json, each served by a stand-in agent behind its own gateway. Their skills' mappings use only triples that exist as policies in the dataset, which a unit test enforces. Three policy actions and one whole agent are left unmapped on purpose, so refusals can be shown as well as routes. Who may reach which gateway is in the graph: a Workflow per agent, CAN_TRIGGER edges from the departments and the customer records a Person holds. Which skills a person may use is in the graph too: Skill nodes under each Agent and the policy person-can-use-skill; a gateway answers the authenticated card with that set only and records the filtering as a DISCOVERY.
