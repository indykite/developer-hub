One prompt, end to end

  1. Mint. The console's demo issuer signs two RS256 JWTs: the persona's subject token (aud intent-demo-console) and the console's own actor token (aud intent_agent). A corporate IdP plays this role in production.
  2. Exchange. RFC 8693 at the Token Service: subject + actor in, a delegation token out, sub = the persona, act.sub = the console, aud = intent_agent, 5 minutes to live. The exchange is audited.
  3. SendMessage. A2A JSON-RPC to the Intent Agent with Authorization: Bearer <delegation>, A2A-Version: 1.0, X-Request-ID, and the caller's subject_type/subject_id in message.metadata.
  4. Introspect. The agent validates the Bearer at the Token Service (RFC 7662, client_secret_basic) and requires aud to contain intent_agent. Inactive or wrong-audience tokens are 401 before the prompt is read.
  5. Vocabulary. The data schema and the caller type's ACTIVE KBAC policies are fetched from the platform with the app agent key, cached in Redis. No policies for the type means a refusal before any model call.
  6. Extract. Gemini answers in a structured schema whose enums are the granted (subject, action, resource) triples; the subject is rebound to the caller afterwards, so prompt text can never impersonate anyone.
  7. Validate and audit. Every evaluation is re-checked against schema and policies, CEL filters are parsed and type-checked, off-schema answers are fed back once; the record with outcome, versions, retries and latency lands on the console's webhook.
  8. Decide. The console maps each evaluation to the AuthZEN endpoint the platform has today and shows the live decision or search results. filters and qualifiers are shown as carried: the AuthZEN API reads input_params only.

Boundaries

Only two things leave the machine: the platform calls (schema, policies, decisions) and the Gemini call made by the agent. Secrets live in .env and in two generated files that git ignores: the Token Service config and the demo issuer key.

The Intent Agent makes no authorization decision. It produces the question, in the AuthZEN shape, from the only vocabulary a policy engine will accept. The decision stays with the engine - which is why the demo shows both halves side by side.

Phase 2

Put an IndyKite Agent Gateway in front of a protected agent and set its intent_agent section to this agent. The gateway resolves the caller with ContX IQ whoami, mints its own token for audience intent_agent, and sends the same SendMessage - the intent then rides along the authorized request. That needs a real IdP and a platform Token Introspect that trusts the user's token.
