One prompt, end to end

  1. Mint. The console's demo issuer signs two RS256 JWTs: the persona's subject token (aud intent-ibac-console) and the console's own actor token (aud intent_agent). A corporate IdP plays this role in production.
  2. Exchange. RFC 8693 at the Token Service: subject + actor in, a delegation token out, sub = the persona, act.sub = the console, aud = intent_agent, 5 minutes to live. The exchange is audited.
  3. SendMessage. A2A JSON-RPC to the Intent Agent with Authorization: Bearer <delegation>, A2A-Version: 1.0, X-Request-ID, and the caller's subject_type/subject_id in message.metadata.
  4. Introspect. The agent validates the Bearer at the Token Service (RFC 7662, client_secret_basic) and requires aud to contain intent_agent. Inactive or wrong-audience tokens are 401 before the prompt is read.
  5. Vocabulary. The data schema and the caller type's ACTIVE KBAC policies are fetched from the platform with the app agent key, cached in Redis. No policies for the type means a refusal before any model call.
  6. Extract. Gemini answers in a structured schema whose enums are the granted (subject, action, resource) triples; the subject is rebound to the caller afterwards, so prompt text can never impersonate anyone.
  7. Validate and audit. Every evaluation is re-checked against schema and policies, CEL filters are parsed and type-checked, off-schema answers are fed back once; the record with outcome, versions, retries and latency lands on the console's webhook.
  8. Decide the intent. The console maps each evaluation to the AuthZEN endpoint the platform has today and shows the live decision or search results. filters and qualifiers are shown as carried: the AuthZEN API reads input_params only.
  9. Discover. The IBAC engine matches the intent against every card of the fleet: a skill matches an evaluation when one of its x-coaz-mappings agrees on subject type, resource type and action. One record per card, IBAC_DISCOVERY, with the skills matched per evaluation.
  10. Confirm. For every matched skill the engine runs usage: it resolves the mapping's ids ($token.sub from the delegation token, $parameters.<name> from the intent) and builds one AuthZEN request per (subject, resource) pair, or declares a search match when an id stays empty. One record per skill, IBAC_USAGE, with the reason code.
  11. Decide the generated requests. The requests the engine built go to the platform through the same mapper as the intent's own evaluations, so the board shows ALLOW or DENY next to each.

Boundaries

Only two things leave the machine: the platform calls (schema, policies, decisions) and the Gemini call made by the agent. Secrets live in .env and in two generated files that git ignores: the Token Service config and the demo issuer key.

The Intent Agent makes no authorization decision. It produces the question, in the AuthZEN shape, from the only vocabulary a policy engine will accept.
The IBAC engine makes no authorization decision either. It answers a narrower question: does this agent declare the skill this intent needs? Discovery routes, usage confirms and names the exact check, the platform decides. In production the engine runs inside the IndyKite Agent Gateway in front of each agent and reads that agent's own card; the console runs the same rules over six cards at once so the routing can be watched.

What the fleet is

Six A2A agent cards in console/data/fleet.json, none of them running: what a gateway would read from /.well-known/agent-card.json. Their skills' mappings use only triples that exist as policies in the intent dataset, which a unit test enforces. Three policy actions and one whole agent are left unmapped on purpose, so refusals can be shown as well as routes.
